The storage layer is the bridge between the SDK's Python objects and FalkorDB's graph database. Two classes handle everything: **GraphStore** manages node and relationship writes, and **VectorStore** manages embeddings, indexes, and search. A third class, **EntityDeduplicator**, handles post-ingestion entity merging.

This document explains how each one works, what Cypher queries they generate, and how to tune them.

---

## The Big Picture

```
SDK Python Objects                    FalkorDB
──────────────────                    ────────
GraphNode          ───GraphStore───>  (:Person {id, name, ...})
GraphRelationship  ───GraphStore───>  ()-[:RELATES {fact, ...}]->()

TextChunks         ───VectorStore──>  (:Chunk {embedding: vecf32(...)})
                   ───VectorStore──>  Vector + Fulltext Indexes

Query vectors      <──VectorStore───  db.idx.vector.queryNodes(...)
Keyword queries    <──VectorStore───  db.idx.fulltext.queryNodes(...)

Duplicate entities ─EntityDeduplicator─> DETACH DELETE + edge remap
```

## GraphStore — Writing Nodes and Relationships

`GraphStore` is the single write path for all graph data. It uses parameterized Cypher to prevent injection and batched `UNWIND` for performance.

### Batched UNWIND MERGE

Nodes and relationships are written in batches of **500 items** per query. The pattern:

```cypher
-- Nodes
UNWIND $batch AS item
MERGE (n:`Person` {id: item.id})
SET n += item.properties
SET n:__Entity__

-- Relationships (with label hints)
UNWIND $batch AS item
MATCH (a:`__Entity__` {id: item.start_id}), (b:`__Entity__` {id: item.end_id})
MERGE (a)-[r:`RELATES`]->(b)
SET r += item.properties
```

**Why MERGE, not CREATE?** MERGE is idempotent — if a node or relationship already exists, it updates the properties rather than creating a duplicate. This makes re-ingestion safe.

### Label Hints

Relationship MATCH queries use **label hints** to speed up endpoint lookups. Instead of searching all nodes, FalkorDB only looks at nodes with the specified label:

| Edge Type | Source Label | Target Label |
|-----------|-------------|-------------|
| `PART_OF` | `Document` | `Chunk` |
| `NEXT_CHUNK` | `Chunk` | `Chunk` |
| `MENTIONED_IN` | `__Entity__` | `Chunk` |
| `RELATES` | `__Entity__` | `__Entity__` |

Unknown edge types default to `(__Entity__, __Entity__)`.

### Per-Item Fallback

If a batch upsert fails (e.g., a single malformed property causes the whole batch to error), GraphStore falls back to **per-item upserts**. The behavior differs slightly: for **nodes**, the first per-item failure raises a `DatabaseError` (remaining items in that batch are not attempted); for **relationships**, failures are logged as warnings and processing continues through the batch.

### None-ID Guard

Before writing, nodes with `None` or empty IDs are filtered out. These come from bad LLM extraction (the LLM sometimes returns entities without proper names). The guard prevents phantom nodes from polluting the graph.

### Property Cleaning

All properties go through `_clean_properties()` before writing:

| Input Type | Treatment |
|-----------|-----------|
| `str`, `int`, `float`, `bool` | Stored as-is |
| `list` | Items filtered to primitives only, empty lists dropped |
| `dict` | Serialized to JSON string |
| `None` | Dropped entirely |
| Other | Converted to string |

### Cypher Safety

Node labels and relationship types are sanitized via `sanitize_cypher_label()` to prevent Cypher injection. Properties are applied via parameter maps (e.g., `SET n += item.properties`), so property keys and values are never interpolated into the Cypher string.

## VectorStore — Embeddings, Indexes, and Search

`VectorStore` handles everything related to vector and fulltext operations.

### Index Creation

**Vector indexes** use FalkorDB's native vector index syntax:

```
CREATE VECTOR INDEX FOR (n:Chunk) ON (n.embedding)
OPTIONS {dimension:256, similarityFunction:'cosine'}
```

**Fulltext indexes** use the RediSearch-based fulltext API:

```
CALL db.idx.fulltext.createNodeIndex('Chunk', 'text')
CALL db.idx.fulltext.createNodeIndex('__Entity__', 'name', 'description')
```

**Relationship vector indexes** use the edge index syntax:

```
CREATE VECTOR INDEX FOR ()-[e:`RELATES`]->() ON (e.embedding)
OPTIONS {dimension:256, similarityFunction:'cosine'}
```

All index creation is idempotent — if the index already exists, the error is silently caught and logged at debug level.

### Chunk Indexing (index_chunks)

When chunks are ingested, their text is embedded and stored:

1. **Batch embed:** All chunk texts are passed to the embedder via a single `aembed_documents` call. The underlying provider controls how these are internally batched (e.g., via a configurable `batch_size`) and may split them across multiple API requests.
2. **Batch write:** Vectors are written to Chunk nodes using UNWIND (500 per batch):
   ```cypher
   UNWIND $batch AS item
   MATCH (c:Chunk {id: item.chunk_id})
   SET c.embedding = vecf32(item.vector)
   ```
3. **Fallback:** If batch embedding fails, chunks are embedded one at a time. If batch writing fails, items are written individually.

### Entity Embedding Backfill (backfill_entity_embeddings)

After all documents are ingested, entity nodes need embeddings for vector search. This is done during `finalize()`:

1. **Query:** Find entities missing embeddings: `WHERE e.embedding IS NULL`
2. **Embed:** Batch-embed entity names via `aembed_documents`
3. **Write:** Store vectors using UNWIND:
   ```cypher
   UNWIND $batch AS item
   MATCH (e:__Entity__ {id: item.eid})
   SET e.embedding = vecf32(item.vector)
   ```
4. **Loop:** Repeat until no more entities with NULL embeddings remain. Each batch naturally returns the next un-embedded set.

### Relationship Embedding (embed_relationships)

RELATES edges with a `fact` property but no embedding are batch-embedded:

1. **Query:** Find edges with `r.embedding IS NULL AND r.fact IS NOT NULL`
2. **Embed:** Batch-embed the `fact` text
3. **Write:** Store vectors on each edge individually (using internal FalkorDB edge IDs):
   ```cypher
   MATCH ()-[r:RELATES]->()
   WHERE id(r) = $rid
   SET r.embedding = vecf32($vector)
   ```

### Search Methods

**Vector search on Chunk nodes:**
```cypher
CALL db.idx.vector.queryNodes('Chunk', 'embedding', $top_k, vecf32($vector))
YIELD node, score
RETURN node.id AS id, node.text AS text, score
ORDER BY score DESC
```

**Vector search on Entity nodes:**
```cypher
CALL db.idx.vector.queryNodes('__Entity__', 'embedding', $top_k, vecf32($vector))
YIELD node, score
RETURN node.id AS id, node.name AS name, node.description AS description, score
ORDER BY score DESC
```

**Vector search on RELATES edges (with fallback):**
```cypher
-- Primary (FalkorDB >= 4.2):
CALL db.idx.vector.queryRelationships('RELATES', 'embedding', $top_k, vecf32($vector))
YIELD relationship AS r, score
RETURN r.src_name, r.rel_type, r.tgt_name, r.fact, score

-- Fallback (Cypher-based cosine distance scan):
MATCH (a:__Entity__)-[r:RELATES]->(b:__Entity__)
WHERE r.embedding IS NOT NULL
WITH a, r, b, vecf32.distance.cosine(r.embedding, vecf32($vector)) AS dist
RETURN r.src_name, r.rel_type, r.tgt_name, r.fact, (1-dist) AS score
ORDER BY dist ASC LIMIT $top_k
```

**Fulltext search:**
```cypher
CALL db.idx.fulltext.queryNodes('Chunk', $query_text)
YIELD node, score
RETURN node.id AS id, node.text AS text, score
ORDER BY score DESC LIMIT $top_k
```

Special characters in fulltext queries are escaped for RediSearch compatibility (commas, brackets, operators, etc.).

### Stored Embedding Optimization

During retrieval, the `rerank_chunks()` function uses **stored embeddings** when possible. Instead of re-embedding all candidate chunks (which would require an expensive API call), it fetches the vectors already stored on Chunk nodes and computes cosine similarity locally. This makes reranking instant when stored embedding coverage is >= 90%.

### ensure_indices()

Creates all 5 standard indexes in one call. Tracks state internally (`_indices_ensured`) to avoid redundant creation. Called automatically after each `ingest()` call, and re-run during `finalize()` (which resets the flag).

## EntityDeduplicator — Merging Duplicate Entities

After ingesting multiple documents, the same real-world entity might exist as multiple nodes (e.g., "Alice" from doc 1 and "Alice Smith" from doc 5). The deduplicator merges them.

**It is incremental.** An entity is *pending* when it has no name vector, or when a `pending` system record lists it (see [SDK system nodes](#sdk-system-nodes)). Ingest writes entities without a vector and marks nothing on them, so a new entity is pending as written. A dedup run lists every entity without a vector in a `pending` record *before* it embeds it, so no crash can leave an unchecked entity looking checked. It then reaches the rest of the graph through indexes — the `__Entity__.embedding` vector index for nearest names, `__Entity__.id` for reads and merges — never by reading every entity. A run clears an entity's record once its check completes, so a second run with nothing pending does no work. An entity ingested while a run works is found by the next one. An entity whose check did not complete stays pending and is retried: a failed lookup or judge call, an answer that was not a clean partition, a group held for one, or a merge an `update()` changed. After 3 judged runs without a usable verdict it becomes *unresolved*: it is reported in `FinalizeResult.dedup_unresolved`, left out of every candidate set and never merged automatically, until `dedup_all=True` retries it. A table re-sync that renames a row drops its vector, so the row is checked under its new name. `deduplicate_entities(dedup_all=True)` / `finalize(dedup_all=True)` checks every entity — once, after vectors were written outside `finalize()`.

**Every merge is decided before any is written.** A run takes the graph's dedup lock (a second concurrent `finalize()` raises `DedupRunActiveError`), decides the merges of both phases below, writes them as a **merge plan**, seals it, and only then applies it. Each merge is **one atomic query** that moves every relationship the duplicate has (every type, both directions), folds its properties into the survivor, deletes it, and ticks itself off in the plan. A crash at any point is picked up by the next run: before sealing, nothing was merged and the work is judged again; after sealing, the next run finishes the plan from its ticks, and nothing is merged twice or half. A run that stalls past the lock's 10-minute heartbeat is taken over, and every write it makes afterwards checks — in the same query — that it still holds the lock, so it changes nothing.

### Phase 1: Exact Name Match (Always Runs)

1. **Fetch** the pending entities with their primary label (the non-`__Entity__` label), and their 10 nearest names from the vector index — searched from the vector stored on each entity — that could share a group with them (same canonical name or an acronym pair); when all 10 do, the lookup widens tenfold for that entity (up to 1,000), so twenty mentions of one name are all found
2. **Group** by `(canonical_name, label)` — the name is case-folded with accents, punctuation, inner dots (`A.I.` = `AI`) and a leading English article removed, `Surname, Given` un-inverted, common abbreviations expanded and one trailing legal form (`Ltd`, `Inc`) dropped; word order and the letters of non-Latin scripts are kept. Grouping by label prevents cross-type merging (Person "Paris" and Location "Paris" stay separate)
3. **Fold acronyms:** a 3–6 letter name joins the group of the *single* same-label entity whose initials it spells (`AIHS` / `Ashford Island Historical Society`). An acronym with several candidate expansions is left alone
4. **For each group with duplicates:**
   - **Who decides:** when a group holds a node a declared table wrote, it merges here by rule, with no LLM. A group of extracted mentions only is handed to the judge (Phase 2) instead when the judge runs — the same spelling is evidence, not proof (Paris, France and Paris, Texas) — and merges here only with `judge=False`
   - **Survivor:** A node a declared table wrote (it carries the row's key, so the table's next re-sync still finds it), then a real node over a placeholder, then the long form over an acronym, then the best-connected node (most RELATES and MENTIONED_IN edges), then the longest description, then the longest name. Two nodes written from declared keys are never merged into each other, whatever they are called
   - **The merge** (applied from the sealed plan): one generated query per duplicate. The SDK reads which relationship types the duplicate has, and generates a block per type and direction that moves those edges to the survivor with the write path's own keys — `RELATES` keyed on `rel_type` with `source_chunk_ids` unioned rather than overwritten, every other type on its endpoints with `SET r += properties`; an edge between the duplicate and the survivor is dropped rather than turned into a self-loop. The survivor is bound before every `MERGE` (a path-`MERGE` with an unbound `(s {id})` creates an empty ghost `__Entity__` node), and every pattern expands from the bound duplicate (anchored on a labelled far end, the planner scans the whole label). In the same query the duplicate's `source_chunk_ids` are unioned into the survivor's, its description is joined onto the survivor's with `" | "` (each member kept once, in `descriptions`), its name is added to the survivor's `aliases` when it is not a spelling variant, and every other property the survivor lacks — a typed column a table signed, `is_stub` — is copied over, a value already on the survivor always winning; then `DETACH DELETE`. The query re-checks that nothing it was generated from has changed — a relationship type it has no block for, or a property ingest rewrote on either node — and writes nothing if so; the merge is read and generated again. An entity deleted, re-keyed or renamed since it was judged makes the merge *changed*: skipped, and its group decided again next run

### Phase 2: LLM-Judged Cross-Document Dedup (Default in `finalize()`)

Ingest resolves per document, so `Airbus` in one file and `Airbus SE` in another never meet until here. `LLMJudgeDeduplicator` (`storage/judge_dedup.py`) decides identity only — it never writes a merge — over the pending entities, with the exact phase's decisions applied in memory (an entity it absorbs is represented by its survivor):

1. **Nominate** candidate pairs without an LLM: the 5 nearest names of each pending entity from the `__Entity__` vector index at cosine ≥ 0.5 (searched from the stored vectors, 250 entities per query, one result row each), plus the same-spelling pairs of extracted mentions and the ambiguous acronym/long-form pairs Phase 1 handed over. Descriptions are not embedded
2. **Group** candidates into dense sets of at most 8: more than half of a set's pairs must be nominated edges, so a chain A–B–C–D where only neighbours are similar (exactly half) cannot form one set (agreements in separate sets still chain, step 4); an edge left between two sets is its own 2-member set. Whole sets are packed into prompts of ≤ 3,000 tokens; the entity text is rendered one line per entity — name, labels, up to 5 existing aliases, description — flattened and quoted, and the prompt tells the model it is untrusted document data
3. **Judge** — the LLM partitions each set into same-referent groups (no similarity scores shown) and gives each group of two or more its best name, copied from the members' names and aliases. Only a clean partition counts: every member exactly once, no member number the set lacks, no merged name on a one-member group. A set without one — a failed call, or a malformed answer — is asked again on its own, up to 2 more times. Every set is judged before anything is merged
4. **Resolve** over the whole run: agreements are unioned across sets — "AAPL" = "Apple Inc." in one set and "Apple Inc." = "Apple" in another become one group — but never into a group holding a pair the judge kept apart in a set, or a protected pair (two keyed rows, a mention two rows could own; neither is ever put to the judge). A group that holds a member of a set that never got a usable answer is **held**: that answer could still change it, so nothing in it merges and its pending members are checked again (one held only because of a neighbour's failed set gets its judged attempt back)
5. **Same → merge**, by the Phase 1 rules and the same single query: survivor by the Phase 1 rank; every member's description kept; other names kept in `aliases`; provenance and missing properties carried; every edge moved. The survivor gains every member's label, as Cypher labels and on record in `merged_labels`, and takes the judge's name for the group when it is one of the members' own names or aliases (its old name moves to `aliases`, and its name vector is replaced; the id does not change; a table row keeps its declared name). The rename is the group's last operation in the plan
6. **Different → nothing** is written to the entities: the pending entity's check is complete, and the pair is put to the judge again only if a later pending entity brings it into a set

gpt-4.1 made 9 wrong merges where gpt-4o-mini made 51 on the benchmark corpus, so pass a gpt-4.1-class `judge_llm`. Statistics (entities, neighbours, candidates, sets, calls, failed calls, agreed pairs, merges decided) are in `EntityDeduplicator.last_judge_stats` and `FinalizeResult.judge_stats`; what the run left — still pending, unresolved, merges skipped as changed — is in `EntityDeduplicator.last_report` and on `FinalizeResult`. `finalize(judge=False)` skips this phase (exact-name dedup only, no model): the pending entities then stay pending, since the judge still owes them a check, and an entity absorbed into one already checked hands its pending state to that survivor; `release_unjudged=True` marks them checked instead. The standalone `deduplicate_entities()` runs the judge only when asked (`judge=True`).

### Running alongside `update()` and deletes

`update()`, `delete_document()` and a table re-sync may run while `finalize()` deduplicates; they never wait. Every SDK query that deletes or re-keys an entity leaves a `deleted` record in the same query while a dedup run is in progress, and a planned merge that would touch such an entity is skipped as changed. FalkorDB runs one write at a time per graph, and each merge and each SDK delete is a single query, so every delete lands either before a merge — which sees the record — or after it, as an ordinary delete. Deletes you issue with your own Cypher are not covered.

### SDK system nodes

The SDK keeps a small, fixed set of its own nodes in the data graph, under two labels, and never anything on your entities:

| Label | Holds | Lifetime |
|---|---|---|
| `__GraphRAGConfig__` | what the data *is*: the embedding model and vector size the stored vectors were written with | as long as the graph |
| `__GraphRAGProcessing__` | dedup work in progress, by `kind`: `run` (the lock: owner, heartbeat), `pending` (entities whose check is owed, with their judged attempts), `unresolved` (entities no longer retried, with the reason and who they were kept from), `deleted` (entities an SDK path removed during a run), and the merge plan (`plan_header`, `plan`, `plan_ids`) | until the work completes; a finished run leaves only `pending` and `unresolved` records still owed |

They live beside the data, not in a graph of their own, because a dedup write must check that its run still owns the lock *in the same query* that changes entities, and a FalkorDB query cannot span two graphs. They have no edges and no vector, so no traversal or search reaches them, and `get_statistics()` does not count them. Range indexes on `kind` and `eid` keep every check one index lookup.

## FalkorDB-Specific Notes

### Version

Entity deduplication requires **FalkorDB 4.20 or later** and refuses older servers with a clear error: before 4.20.0 every write to a node holding a vector left a stale copy in the vector index, and searches returned fewer neighbours than asked for (measured: 2–3 of 6 after one write) — a dedup run writes vectors and merges into embedded nodes on every run.

### Vector Storage

FalkorDB stores vectors as `vecf32` — a native 32-bit float vector type. All vectors in the SDK are stored via:
```cypher
SET n.embedding = vecf32($vector)
```

### Vector Search API

Node vector search uses 4 arguments:
```
db.idx.vector.queryNodes('Label', 'property', $top_k, vecf32($vector))
```

Relationship vector search (FalkorDB >= 4.2):
```
db.idx.vector.queryRelationships('RELATES', 'embedding', $top_k, vecf32($vector))
```

### Graph Deletion

For fast graph deletion, use `GRAPH.DELETE` (the Redis-level command):
```python
await rag.graph_store.delete_all()  # Uses GRAPH.DELETE internally
```
This is much faster than `MATCH (n) DETACH DELETE n` on large graphs.

### Retry Behavior

The connection layer retries transient query failures up to 3 times using exponential backoff with jitter (`retry_delay * 2^attempt * random(0.5, 1.5)`) and employs a circuit breaker to short-circuit repeated failures. Non-transient errors (containing "already indexed", "already exists", or "unknown index") are raised immediately.
