The storage layer is the bridge between the SDK's Python objects and FalkorDB's graph database. Two classes handle everything: **GraphStore** manages node and relationship writes, and **VectorStore** manages embeddings, indexes, and search. A third class, **EntityDeduplicator**, handles post-ingestion entity merging, with a **DedupJudge** deciding which candidates are the same entity.

This document explains how each one works, what Cypher queries they generate, and how to tune them.

<Warning>
GraphRAG SDK requires **FalkorDB 4.20 or later**. An older server is refused before anything is written, with `FalkorDBVersionError`. See [Version](#version) below for why, and for the upgrade order.
</Warning>

## The Big Picture

```
SDK Python Objects                    FalkorDB
──────────────────                    ────────
GraphNode          ───GraphStore───>  (:Person {id, name, ...})
GraphRelationship  ───GraphStore───>  ()-[:RELATES {fact, ...}]->()

TextChunks         ───VectorStore──>  (:Chunk {embedding: vecf32(...)})
                   ───VectorStore──>  Vector + Fulltext Indexes

Query vectors      <──VectorStore───  db.idx.vector.queryNodes(...)
Keyword queries    <──VectorStore───  db.idx.fulltext.queryNodes(...)

Duplicate entities ─EntityDeduplicator─> one query: every edge moved, then DETACH DELETE
```

## GraphStore — Writing Nodes and Relationships

`GraphStore` is the single write path for all graph data. It uses parameterized Cypher to prevent injection and batched `UNWIND` for performance.

### Batched UNWIND MERGE

Nodes and relationships are written in batches of **500 items** per query. The pattern:

```cypher
-- Entity nodes
UNWIND $batch AS item
MERGE (n:`Person` {id: item.id})
WITH n, item,
     coalesce(n.source_chunk_ids, []) AS old,
     coalesce(item.properties.source_chunk_ids, []) AS contrib
SET n += item.properties
SET n.source_chunk_ids = CASE WHEN size(contrib) = 0 THEN n.source_chunk_ids
                         ELSE old + [c IN contrib WHERE NOT c IN old] END
SET n:__Entity__

-- RELATES edges (with label hints), keyed on rel_type as well as the pair
UNWIND $batch AS item
MATCH (a:`__Entity__` {id: item.start_id}), (b:`__Entity__` {id: item.end_id})
MERGE (a)-[r:`RELATES` {rel_type: coalesce(item.properties.rel_type, '')}]->(b)
WITH r, item,
     coalesce(r.source_chunk_ids, []) AS old,
     coalesce(item.properties.source_chunk_ids, []) AS contrib
SET r += item.properties
SET r.source_chunk_ids = old + [c IN contrib WHERE NOT c IN old]
```

Structural nodes (`Document`, `Chunk`) and every other edge type use a plain `MERGE ... SET n += item.properties`, keyed on `id` for nodes and on the two endpoints for edges.

**Why MERGE, not CREATE?** MERGE is idempotent — if a node or relationship already exists, it updates the properties rather than creating a duplicate. This makes re-ingestion safe.

**Edge identity includes `rel_type`.** Every extracted fact is a `RELATES` edge with its semantic type in `rel_type`, so `Alice WORKS_AT Acme` and `Alice FOUNDED Acme` are two edges between the same two nodes. Keying the `MERGE` on the endpoints alone would keep one edge per pair and overwrite the other fact.

**Provenance is a union.** An entity's `source_chunk_ids`, and a `RELATES` edge's, list every chunk that mentioned it across documents. Each write appends the chunks the node or edge does not have yet, instead of replacing the list, and a write that carries no list (a table row, a re-embed) leaves it alone. `update()` and `delete_document()` remove the chunks they delete from every entity the document touched.

### Repeated Keys in One Batch

A batch can hold the same entity or relationship twice, for example an entity seen in two chunks of one document. FalkorDB resolves a repeated key inside one `UNWIND ... MERGE` differently by engine (4.x kept the first row's values, 6.0.x the last), and only one row's `source_chunk_ids` survived on either. `upsert_nodes()` and `upsert_relationships()` therefore merge rows that share a key before sending the batch, as if they were written one at a time: later properties win, and for entities and `RELATES` edges the chunk lists are combined. Other labels and edge types keep the last write's list.

### Range Indexes on `id`

Every write is `MERGE (n:Label {id: ...})`, and a `MERGE` can only use an index on the label in its own pattern. Without one, writing *n* nodes costs O(n²): 4,000 table rows took 15.2 s, and take 1.9 s with the index. So before it first writes into a label, `GraphStore` creates range indexes on `id` and `entity_key` for that label (and on `__Entity__.id`, which relationship writes match endpoints by). `ensure_indices()` also creates `id` range indexes on `Document`, `Chunk` and `__Entity__`. The indexes the graph already has are read once per store, so reopening a graph creates nothing and logs nothing. `delete_all()` resets this memory along with the graph.

### Label Hints

Relationship MATCH queries use **label hints** to speed up endpoint lookups. Instead of searching all nodes, FalkorDB only looks at nodes with the specified label:

| Edge Type | Source Label | Target Label |
|-----------|-------------|-------------|
| `PART_OF` | `Document` | `Chunk` |
| `NEXT_CHUNK` | `Chunk` | `Chunk` |
| `MENTIONED_IN` | `__Entity__` | `Chunk` |
| `RELATES` | `__Entity__` | `__Entity__` |

Unknown edge types default to `(__Entity__, __Entity__)`.

### Per-Item Fallback

If a batch upsert fails (e.g., a single malformed property causes the whole batch to error), GraphStore falls back to **per-item upserts**. The behavior differs slightly: for **nodes**, the first per-item failure raises a `DatabaseError` (remaining items in that batch are not attempted); for **relationships**, failures are logged as warnings and processing continues through the batch.

### None-ID Guard

Before writing, nodes with `None` or empty IDs are filtered out. These come from bad LLM extraction (the LLM sometimes returns entities without proper names). The guard prevents phantom nodes from polluting the graph.

### Property Cleaning

All properties go through `_clean_properties()` before writing:

| Input Type | Treatment |
|-----------|-----------|
| `str`, `int`, `float`, `bool` | Stored as-is (control characters are stripped from strings) |
| `list` | Items filtered to primitives only, empty lists dropped |
| `dict` | Serialized to JSON string |
| `None` | Dropped entirely |
| Other | Converted to string |

### Cypher Safety

Node labels and relationship types are sanitized via `sanitize_cypher_label()` to prevent Cypher injection. Properties are applied via parameter maps (e.g., `SET n += item.properties`), so property keys and values are never interpolated into the Cypher string.

## VectorStore — Embeddings, Indexes, and Search

`VectorStore` handles everything related to vector and fulltext operations.

### Index Creation

**Vector indexes** use FalkorDB's native vector index syntax:

```
CREATE VECTOR INDEX FOR (n:Chunk) ON (n.embedding)
OPTIONS {dimension:256, similarityFunction:'cosine'}
```

**Fulltext indexes** use the fulltext index DDL, one field per statement:

```
CREATE FULLTEXT INDEX FOR (n:Chunk) ON (n.text)
CREATE FULLTEXT INDEX FOR (n:__Entity__) ON (n.name)
CREATE FULLTEXT INDEX FOR (n:__Entity__) ON (n.description)
```

FalkorDB 6.0.x rejects the older `db.idx.fulltext.createNodeIndex(label, field, ...)` procedure.

**Relationship vector indexes** use the edge index syntax:

```
CREATE VECTOR INDEX FOR ()-[e:RELATES]->() ON (e.embedding)
OPTIONS {dimension:256, similarityFunction:'cosine'}
```

All index creation is idempotent — if the index already exists, the error is silently caught and logged at debug level.

### Chunk Indexing (index_chunks)

When chunks are ingested, their text is embedded and stored:

1. **Batch embed:** All chunk texts are passed to the embedder via a single `aembed_documents` call. The underlying provider controls how these are internally batched (e.g., via a configurable `batch_size`) and may split them across multiple API requests.
2. **Batch write:** Vectors are written to Chunk nodes using UNWIND (500 per batch):
   ```cypher
   UNWIND $batch AS item
   MATCH (c:Chunk {id: item.chunk_id})
   SET c.embedding = vecf32(item.vector)
   ```
3. **Fallback:** If batch embedding fails, chunks are embedded one at a time. If batch writing fails, items are written individually.

### Entity Embedding Backfill (backfill_entity_embeddings)

Embeds entity nodes that have no name vector. `finalize()` does not call it: dedup embeds every entity, listing it as pending first. Called directly it is not a dedup step — an entity with a vector and no pending record counts as checked — so run `finalize(dedup_all=True)` once afterwards. It runs these steps:

1. **Query:** Find entities missing embeddings: `WHERE e.embedding IS NULL`
2. **Embed:** Batch-embed entity names via `aembed_documents`
3. **Write:** Store vectors using UNWIND:
   ```cypher
   UNWIND $batch AS item
   MATCH (e:__Entity__ {id: item.eid})
   SET e.embedding = vecf32(item.vector)
   ```
4. **Loop:** Repeat until no more entities with NULL embeddings remain. Each batch naturally returns the next un-embedded set.

### Relationship Embedding (embed_relationships)

RELATES edges with a `fact` property but no embedding are batch-embedded:

1. **Query:** Find edges with `r.embedding IS NULL AND r.fact IS NOT NULL`
2. **Embed:** Batch-embed the `fact` text
3. **Write:** Store vectors on each edge individually (using internal FalkorDB edge IDs):
   ```cypher
   MATCH ()-[r:RELATES]->()
   WHERE id(r) = $rid
   SET r.embedding = vecf32($vector)
   ```

### Search Methods

FalkorDB's vector procedures yield a cosine *distance* in `score`. Every vector search turns it into a similarity, `1 - score`, so in every result **a higher score means a closer match**, and results are ordered highest first.

**Vector search on Chunk nodes:**
```cypher
CALL db.idx.vector.queryNodes('Chunk', 'embedding', $fetch_k, vecf32($vector))
YIELD node, score
RETURN node.id AS id, node.text AS text, (1-score) AS score
ORDER BY score DESC, id
```

**Vector search on Entity nodes:**
```cypher
CALL db.idx.vector.queryNodes('__Entity__', 'embedding', $fetch_k, vecf32($vector))
YIELD node, score
RETURN node.id AS id, node.name AS name, node.description AS description, (1-score) AS score
ORDER BY score DESC, id
```

Equally close nodes are cut by id, not by the order the engine lists them (FalkorDB 4.x and 6.0.x differ). To see every tie at the cut, the query asks the index for `$fetch_k` = 2×`top_k` nodes, and asks again for twice as many (up to 1024) while the score at the cut still equals the score of the last node fetched, since the tie may continue past it.

**Vector search on RELATES edges (with fallback):**
```cypher
-- Primary (edge vector index):
CALL db.idx.vector.queryRelationships('RELATES', 'embedding', $top_k, vecf32($vector))
YIELD relationship AS r, score
RETURN r.src_name AS src, r.rel_type AS type, r.tgt_name AS tgt, r.fact AS fact, (1-score) AS score
ORDER BY score DESC

-- Fallback (Cypher-based cosine distance scan):
MATCH (a:__Entity__)-[r:RELATES]->(b:__Entity__)
WHERE r.embedding IS NOT NULL
WITH a, r, b, vec.cosineDistance(r.embedding, vecf32($vector)) AS dist
RETURN r.src_name AS src, r.rel_type AS type, r.tgt_name AS tgt, r.fact AS fact, (1-dist) AS score
ORDER BY dist ASC LIMIT $top_k
```

The scan runs when the server rejects the primary query (FalkorDB 4.x does when there is no `RELATES` vector index, or while it is still being built), or when it returns no rows and `db.indexes()` shows no built vector index on `RELATES.embedding` (FalkorDB 6.0.x answers a missing index with no rows). With the index in place, an empty answer is returned as is. If FalkorDB is unreachable, or the primary query runs past its timeout, the search returns no results without scanning: the scan would fail the same way or take longer still. The scan reads every embedded edge, so the SDK logs a warning the first time a store falls back to it.

**Fulltext search:**
```cypher
CALL db.idx.fulltext.queryNodes('Chunk', $query_text)
YIELD node, score
RETURN node.id AS id, node.text AS text, score
ORDER BY score DESC, id LIMIT $top_k
```

Entity fulltext search ranks by name before score. The index covers `name` and `description` alike, so for a common term every hit can score the same, and an entity named by the query would rank no higher than the ones whose descriptions merely mention it. Results come back in this order: an exact name match (case-insensitive, ignoring surrounding spaces), then names containing the query, then by score, then by id.

Special characters in fulltext queries are escaped for RediSearch compatibility (commas, brackets, operators, etc.).

### Stored Embedding Optimization

During retrieval, the `rerank_chunks()` function uses **stored embeddings** when possible. Instead of re-embedding all candidate chunks (which would require an expensive API call), it fetches the vectors already stored on Chunk nodes and computes cosine similarity locally. This makes reranking instant when stored embedding coverage is >= 90%.

### ensure_indices()

Creates, in one call, the `id` range indexes on `Document`, `Chunk` and `__Entity__`, and the five search indexes: the `Chunk`, `__Entity__` and `RELATES` vector indexes and the `Chunk` and `__Entity__` fulltext indexes. It returns a dict naming each (`range_ids`, `vector_Chunk`, `vector_Entity`, `vector_RELATES`, `fulltext_Chunk`, `fulltext_Entity`) with whether it is in place after this call — `True` whether it was created now or already existed, `False` when creation failed — which `finalize()` reports as `FinalizeResult.indexes`. Tracks state internally (`_indices_ensured`) to avoid redundant creation, and returns `{}` when an earlier call already ensured everything. Called automatically after each prose `ingest()` and each `update()` that writes (a table's first ingest creates only the range indexes it writes through), and re-run during `finalize()` (which resets the flag, so `finalize()` always reports every key).

FalkorDB builds an index over existing data in the background after `CREATE ... INDEX` returns, and a vector search on it finds nothing until the build ends. `ensure_indices()` therefore waits until `db.indexes()` reports every index built before it returns (up to 10 minutes, logging progress every 10 s), so a search right after `ingest()` sees the data.

## EntityDeduplicator — Merging Duplicate Entities

After ingesting multiple documents, the same real-world entity might exist as multiple nodes (e.g., "Alice" from doc 1 and "Alice Smith" from doc 5). The deduplicator merges them.

**It is incremental.** An entity is *pending* when it has no name vector, or when a `pending` system record lists it (see [SDK system nodes](#sdk-system-nodes)). Ingest writes entities without a vector and marks nothing on them, so a new entity is pending as written. A dedup run lists every entity without a vector in a `pending` record *before* it embeds it, so no crash can leave an unchecked entity looking checked. It then reaches the rest of the graph through indexes — the `__Entity__.embedding` vector index for nearest names, `__Entity__.id` for reads and merges — never by loading every entity; finding the entities without a vector is one scan in windows of internal node ids. A run clears an entity's record once its check completes, so a second run with nothing pending does no work. An entity ingested while a run works is found by the next one. An entity whose check did not complete stays pending and is retried: a failed lookup or judge call, an answer that was not a clean partition, a group held for one, or a merge an `update()` changed. Each run that puts it before the judge charges it one attempt, given back only when it was held for a neighbour's failed set or kept pending by a failed lookup alone; after 3 charged runs whose check did not complete (no usable verdict, a run interrupted mid-judging, or a merge an `update()` changed), the next run makes it *unresolved*: it is reported in `FinalizeResult.dedup_unresolved`, left out of every candidate set and never merged automatically, until `dedup_all=True` retries it. A table re-sync that renames a row drops its vector, so the row is checked under its new name. `deduplicate_entities(dedup_all=True)` / `finalize(dedup_all=True)` checks every entity — once, after vectors were written outside `finalize()` — and retries the unresolved ones. An entity with no name (a fact row keyed on a reading id) is given the vector of its id, as retrieval embeds it, and is never listed: the judge cannot judge a name it does not have.

The cost follows the pending entities, not the graph. Measured: adding 1,000 entities to a graph of about 39,000 finalized in 4.5 s with a fake LLM, where the earlier whole-graph flow spent about 256 s and 5,982 LLM calls on dedup on every call. On a labeled set of 277 entities (138 true pairs, gpt-4.1, 3 runs), precision rose from 0.81 to 0.92–0.93 and F1 from 0.71–0.73 to 0.83–0.84, with 5 LLM calls instead of 14.

**Every merge is decided before any is written.** A run takes the graph's dedup lock — one run per graph at a time: a second `finalize()` or `deduplicate_entities()`, from another process or on the same `GraphRAG`, raises `DedupRunActiveError` as soon as it reaches dedup (for `finalize()`, after its first step, the stub cleanup) and leaves the running one untouched — then decides the merges of both phases below, writes them as a **merge plan**, seals it, and only then applies it. Each merge is **one atomic query** that moves every relationship the duplicate has (every type, both directions), folds its properties into the survivor, deletes it, and ticks itself off in the plan. A crash at any point is picked up by the next run: before sealing, nothing was merged and the work is judged again; after sealing, the next run finishes the plan from its ticks, and nothing is merged twice or half. A live run refreshes its heartbeat every 30 s. A run that stalls past the lock's 10-minute heartbeat is taken over, and every write it makes afterwards checks — in the same query — that it still holds the lock, so it changes nothing. A run that stops with a sealed plan unfinished leaves its lock expired rather than released, so the next run takes it at once and finishes the plan first.

<Note>
`DedupRunActiveError` is exported from `graphrag_sdk`. Catch it when several workers may call `finalize()` on one graph. Nothing is lost by it: whatever is still pending when the running run finishes, including entities ingested while it worked, is checked by the next `finalize()`.
</Note>

### Phase 1: Exact Name Match (Always Runs)

1. **Fetch** the pending entities with their primary label (the non-`__Entity__` label), and their 10 nearest names from the vector index — searched from the vector stored on each entity — that could share a group with them (same canonical name or an acronym pair); when all 10 do, the lookup widens tenfold for that entity (up to 1,000), so twenty mentions of one name are all found
2. **Group** by `(canonical_name, label)` — the name is case-folded with accents, punctuation, apostrophes (`O'Brien` = `OBrien`), inner dots (`A.I.` = `AI`) and a leading English article removed, `&` read as `and`, `Surname, Given` un-inverted, common abbreviations expanded (`Corp.` → `corporation`, `Intl` → `international`) and one trailing legal form (`Ltd`, `Inc`, `GmbH`, `LLC`, `PLC`, ...) dropped. Words that are also ordinary words — `Group`, `Holding`, `Co`, `Company` — are not dropped, so `Sony Group Corporation` and `Sony Corporation` stay apart. Word order is kept (`Morgan Stanley` and `Stanley Morgan` stay apart), and so are the letters of non-Latin scripts (`Отдел 5` and `Кабинет 5` stay apart) and a symbol glued to a word (`C`, `C#` and `C++` stay apart, while `C#` still equals `C Sharp`). Grouping by label prevents cross-type merging (Person "Paris" and Location "Paris" stay separate)
3. **Fold acronyms:** a 3–6 letter name joins the group of the *single* same-label entity whose initials it spells (`AIHS` / `Ashford Island Historical Society`). An acronym with several candidate expansions is left alone
4. **For each group with duplicates:**
   - **Who decides:** when a group holds a node a declared table wrote, it merges here by rule, with no LLM. A group of extracted mentions only is handed to the judge (Phase 2) instead — the same spelling is evidence, not proof (Paris, France and Paris, Texas) — and so is a group holding an entity whose nearest-name search did not finish: a second row of the name may lie past what it found
   - **Survivor:** A node a declared table wrote (it carries the row's key, so the table's next re-sync still finds it), then a real node over a placeholder, then the long form over an acronym, then the best-connected node (most RELATES and MENTIONED_IN edges), then the longest description, then the longest name, then the id, so a tie settles the same way on every run. Two nodes written from declared keys are never merged into each other, whatever they are called. A mention whose name two keyed rows share joins neither row: it is left apart, kept from the judge and listed in `FinalizeResult.probable_duplicates`
   - **The merge** (applied from the sealed plan): one generated query per duplicate. The SDK reads which relationship types the duplicate has, and generates a block per type and direction that moves those edges to the survivor with the write path's own keys — `RELATES` keyed on `rel_type` with `source_chunk_ids` unioned rather than overwritten, every other type on its endpoints with `SET r += properties`; an edge between the duplicate and the survivor is dropped rather than turned into a self-loop. The survivor is bound before every `MERGE` (a path-`MERGE` with an unbound `(s {id})` creates an empty ghost `__Entity__` node), and every pattern expands from the bound duplicate (anchored on a labelled far end, the planner scans the whole label). In the same query the duplicate's `source_chunk_ids` are unioned into the survivor's, its description is joined onto the survivor's with `" | "` (each member kept once, in `descriptions`), its name is added to the survivor's `aliases` when it is not a spelling variant, and every other property the survivor lacks — a typed column a table signed, `is_stub` — is copied over. A property both hold with **different** values is a collision, and neither value is lost: the one the judge chose stays (its `KEEP`, on a judged merge), otherwise the survivor's, and the other is appended to `<property>__dropped` on the survivor — a list that later merges add to (two list values are unioned instead); `FinalizeResult.dedup_collisions` names each. Then `DETACH DELETE`. The query re-checks that nothing it was generated from has changed — a relationship type it has no block for, a property of the duplicate added, removed or changed, a new value on the survivor for one of those keys, or a label added to or removed from either node — and writes nothing if so; the merge is read and generated again. An entity deleted, re-keyed or renamed since it was judged makes the merge *changed*: skipped, and its group decided again next run
5. **A declared type beats a guessed one.** The exact phase never merges across labels, with one exception. When a name exists under exactly one label a [table mapping](/structured-ingestion) declared and under one or more labels nothing declared, the declared entity absorbs the guesses: a `Concept` the extractor guessed for "Carbon Farming" joins the `MitigationPractice` a mapping declared. The adopted node's labels do not carry over, since its label was the guess being corrected. This applies only to declared labels outside the built-in entity types (`Person`, `Organization`, ...), because the extractor always had those and a different label there was a choice, not a fallback. Two declared labels sharing a name stay apart, and so does a name two rows of the declared label share. Names left under more than one label are reported in `FinalizeResult.unmerged_name_collisions`

### Phase 2: Judged Cross-Document Dedup

Ingest resolves per document, so `Airbus` in one file and `Airbus SE` in another never meet until here. Every run has a judge: a [`DedupJudge`](/strategies#7-dedupjudge), `LLMJudge` with the GraphRAG LLM unless `finalize(judge=...)` is given another. The run (`storage/judge_dedup.py`) nominates the candidates and checks every answer; the judge decides identity only — it is given sets and returns verdicts, and never writes a merge. It works over the pending entities, with the exact phase's decisions applied in memory (an entity it absorbs is represented by its survivor):

1. **Nominate** candidate pairs without an LLM: the 5 nearest names of each pending entity from the `__Entity__` vector index at cosine ≥ 0.5 (searched from the stored vectors, up to 250 entities per query and at most 2,500 result rows per query, so a wide lookup stays well inside the query timeout), plus the same-spelling pairs of extracted mentions and the ambiguous acronym/long-form pairs Phase 1 handed over. Descriptions are not embedded
2. **Group** candidates into dense sets of at most 8: more than half of a set's pairs must be nominated edges, so a chain A–B–C–D where only neighbours are similar (exactly half) cannot form one set (agreements in separate sets still chain, step 4); an edge left between two sets is its own 2-member set. Whole sets are packed into prompts of ≤ 3,000 tokens; the entity text is rendered one line per entity — name, labels, up to 5 existing aliases, description, and the values it holds for the attributes your ontology declares for its type(s) (`born: 1960; role: "CEO"`) — flattened and quoted, and the prompt tells the model it is untrusted document data. Each prompt opens with the types its members carry and their declared attributes (only those types, not the whole ontology); a node already merged under two types shows the attributes of both
3. **Judge** — the judge partitions each set into same-referent groups (no similarity scores shown) and gives each group of two or more its best name, copied from the members' names and aliases. Two different values of a fact that does not change (a birth or founding date, a birthplace, an identifier) mean different entities; a value only one side holds is not a contradiction; a value that changes over time (an age, a title) is weak evidence. Where a group's members disagree on an attribute, the judge also says whose value the merged entity keeps (`| KEEP: born=1`): a member number, never a value it writes itself. Measured on a small labelled set (gpt-4.1): namesakes told apart only by a birth year or birthplace were merged every time without the values shown, and kept apart every time with them. The answer lists only groups of two or more (`SET 1 GROUP: 1, 4 | NAME: …`), or `SET 2 NONE` for a set where nothing merges; a member no line lists is a different entity from the rest of its set. Leaving out the one-member lines cut answer tokens by about two thirds. The answer ends with the line `END`: since unlisted members count as different, an answer cut short after a group line would otherwise turn the groups it never reached into "different" verdicts. Without `END`, the set of a last group line is unanswered (a last `NONE` line closed its set, so a forgotten `END` there costs nothing). `LLMJudge` usually reuses the GraphRAG LLM, so an output limit set on it for short answers (`max_tokens`) is raised to 4,096 for judge calls (`LLMJudge(min_output_tokens=)` sets the floor; `None` keeps the LLM's own limit, for a server with a small context window); it never sets a limit itself, since a reasoning model spends output tokens on thought. (This step describes `LLMJudge`; a judge of your own gets the same sets as `JudgeSet`s and answers with `SetVerdict`s.) Whatever the judge, an answer counts only when it is clean — no member the set lacks, no member in two groups, no merged name or `KEEP` on a one-member group; a set without one — a failed call, a malformed answer, or one cut before `END` — is asked again (`retry=True`; `LLMJudge` then asks it on its own), up to 2 more times. Every set is judged before anything is merged
4. **Resolve** over the whole run: agreements are unioned across sets — "AAPL" = "Apple Inc." in one set and "Apple Inc." = "Apple" in another become one group — but never into a group holding a pair the judge kept apart in a set, or a protected pair (two keyed rows, a mention two rows could own; neither is ever put to the judge). A group that holds a member of a set that never got a usable answer is **held**: that answer could still change it, so nothing in it merges and its pending members are checked again (one held only because of a neighbour's failed set gets its judged attempt back)
5. **Same → merge**, by the Phase 1 rules and the same single query: survivor by the Phase 1 rank; every member's description kept; other names kept in `aliases`; provenance and missing properties carried; every edge moved. The survivor gains every member's label, as Cypher labels and on record in `merged_labels`, and takes the judge's name for the group when it is one of the members' own names or aliases (its old name moves to `aliases`, and its name vector is replaced; the id does not change; a table row keeps its declared name). The rename is the group's last operation in the plan
6. **Different → nothing** is written to the entities: the pending entity's check is complete, and the pair is put to the judge again only if a later pending entity brings it into a set

gpt-4.1 made 9 wrong merges where gpt-4o-mini made 51 on the benchmark corpus, so give `LLMJudge` a gpt-4.1-class model: `finalize(judge=LLMJudge(gpt41))`. There is no run without a judge — `judge=False` raises `TypeError` — so nothing waits for a judged run that may never come. A run with nothing pending asks the judge nothing.

#### The judge component

```python
from graphrag_sdk import DedupJudge, JudgeGroup, JudgeSet, LLMJudge, SetVerdict

# The default: LLMJudge with the GraphRAG instance's llm.
await rag.finalize()

# Another model for the judge only.
await rag.finalize(judge=LLMJudge(judge_llm, max_concurrency=None, min_output_tokens=4096))

# A judge of your own: no LLM at all.
class SpellingJudge(DedupJudge):
    async def judge(self, sets: list[JudgeSet], *, retry: bool = False) -> list[SetVerdict | None]:
        verdicts = []
        for s in sets:
            by_name: dict[str, list[int]] = {}
            for i, ent in enumerate(s.entities):
                by_name.setdefault(ent.name.casefold(), []).append(i)
            verdicts.append(SetVerdict(groups=[
                JudgeGroup(members=m) for m in by_name.values() if len(m) > 1
            ]))
        return verdicts

await rag.finalize(judge=SpellingJudge())
```

- **`JudgeSet`** — one candidate set: `entities` (each a `JudgeEntity` with `name`, `labels`, `aliases`, `description` and `attributes`, the values it holds for its types' declared attributes) and `types` (each a `JudgeType` with `label`, `description` and its declared `attributes`).
- **`SetVerdict`** — the answer for one set: `groups`, a list of `JudgeGroup(members=[positions], name=None, keep={})`. `name` is the merged entity's name and is used only when it is one of the members' own names or aliases; `keep` maps an attribute to the member whose value the merged entity keeps. A member no group lists is a different entity from the rest of its set. Return `None` for a set the judge could not decide.
- **`retry=True`** marks a second or third ask of sets that got no usable answer; `LLMJudge` then sends one set per prompt.
- **`usage()`** — optional running totals of what the judge spent, as whole numbers. The run adds what it spent to `judge_stats`. `LLMJudge` reports `llm_calls` (prompts sent) and `llm_failed` (prompts that got no response).
- **`LLMJudge(llm, *, max_concurrency=None, min_output_tokens=4096)`** — `max_concurrency=None` uses the LLM's own; `min_output_tokens` is the output floor described in step 3, and `None` keeps the LLM's own limit.

Whatever the judge, the run checks each answer, re-asks a set without a usable one, and keeps the merge itself. See [Strategies](/strategies#7-dedupjudge) for more.

#### Statistics and the report

`FinalizeResult.judge_stats` (also `EntityDeduplicator.last_judge_stats`) holds the judged phase's counts: `entities`, `neighbours`, `candidates`, `sets`, `judge_calls` (rounds: the first ask and each re-ask), `judge_failed`, `unanswered_sets`, `agreed_pairs`, `merged`, and whatever the judge reports through `usage()` (`llm_calls` and `llm_failed` for `LLMJudge`). `FinalizeResult.judge_calls` repeats the round count; the number of LLM prompts is `judge_stats["llm_calls"]`. What the run left — still pending, unresolved, merges skipped as changed, property collisions — is in `EntityDeduplicator.last_report` and on `FinalizeResult` (see [Incremental Updates](/incremental-updates#finalizeresult)).

### What a Merge Keeps

Every merge, by rule or by the judge, keeps what the duplicate carried:

| What | How it is kept |
|---|---|
| Relationships | Every relationship of every type and direction moves to the survivor. `RELATES` edges stay keyed on `rel_type` with `source_chunk_ids` unioned; an edge between the two nodes is dropped rather than turned into a self-loop |
| Description | Each member's description is kept once in the `descriptions` list, and `description` is that list joined with `" \| "` |
| Name | The duplicate's name, and its own aliases, go to the survivor's `aliases` (a spelling variant of the survivor's name is not added). A judged group may also rename the survivor to the judge's name; the old name moves to `aliases`, the id does not change, and the name vector is replaced. A table row keeps its declared name |
| Labels | A judged merge gives the survivor every member's label, as real Cypher labels and on record in `merged_labels` (a `" \| "`-joined string), so a later merge carries them on. A merge by rule carries only the labels the duplicate had itself absorbed; an adoption carries none |
| Provenance | The node-level `source_chunk_ids` are unioned |
| Properties | A property only the duplicate has is copied. Where both hold different values, the judge's `KEEP` pick stays (on a judged merge), otherwise the survivor's, and the other value is appended to `<property>__dropped` (a list) on the survivor. Two list values are unioned instead. Each collision is named in `FinalizeResult.dedup_collisions` |

### Deprecated Arguments

The fuzzy name-embedding phase is removed: finalize-time dedup is the exact phase plus the judge. `deduplicate_entities()` still accepts `fuzzy=False` and `similarity_threshold=` for now, ignored, with a `DeprecationWarning`; `fuzzy=True` raises `ValueError`. Ingest-time resolvers (`ingest(resolver=...)`) are unchanged.

<Note>
`finalize()` and `deduplicate_entities()` call the LLM through the default `LLMJudge`. To keep dedup LLM-free, pass a `DedupJudge` of your own, such as the `SpellingJudge` above.
</Note>

### Running alongside `update()` and deletes

`update()`, `delete_document()` and a table re-sync may run while `finalize()` deduplicates; they never wait. Every SDK query that deletes or re-keys an entity leaves a `deleted` record in the same query while a dedup run is in progress, and a planned merge that would touch such an entity is skipped as changed. FalkorDB runs one write at a time per graph, and each merge and each SDK delete is a single query, so every delete lands either before a merge — which sees the record — or after it, as an ordinary delete. Deletes you issue with your own Cypher are not covered.

A table re-sync that re-keys a renamed row into an id another node already holds folds the two nodes in one query, the same way a merge does: every edge type moves, and nothing is written if either node changed since it was read — a property, an edge type, or a label (for example after `rename_entity()`). The folded node is pending dedup again, since no run has seen it with the row's identity.

### SDK system nodes

The SDK keeps a small, fixed set of its own nodes in the data graph, under two labels, and never anything on your entities:

| Label | Holds | Lifetime |
|---|---|---|
| `__GraphRAGConfig__` | what the data *is*: the embedding model and vector size the stored vectors were written with | as long as the graph |
| `__GraphRAGProcessing__` | dedup work in progress, by `kind`: `run` (the lock: owner, heartbeat), `pending` (entities whose check is owed, with their judged attempts), `unresolved` (entities no longer retried, with the reason and who they were kept from), `deleted` (entities an SDK path removed during a run), and the merge plan (`plan_header`, `plan`, `plan_ids`) | until the work completes; a finished run leaves only `pending` and `unresolved` records still owed (and, after a run that had nothing to plan, the `deleted` records of deletes made while it ran, cleared by the next run) |

They live beside the data, not in a graph of their own, because a dedup write must check that its run still owns the lock *in the same query* that changes entities, and a FalkorDB query cannot span two graphs. They have no edges and no vector, so no traversal or search reaches them, and `get_statistics()` does not count them: its `node_count` subtracts them and its `entity_types` leaves out every `__GraphRAG*` label. Range indexes on `kind` and `eid` keep every check one index lookup.

## FalkorDB-Specific Notes

### Version

GraphRAG SDK requires **FalkorDB 4.20 or later**. Before 4.20.0 every write to a node holding a vector left a stale copy in the vector index, and searches returned fewer neighbours than asked for (measured: 2–3 of 6 after one write) — and ingest, `update()` and dedup all write to such nodes. Each connection asks the server its version once, before its first query (and again after `close()`), and refuses an older one with `FalkorDBVersionError` (a `DatabaseError`), so nothing is written to it: `ingest()`, `query()`, `finalize()` and the rest fail at once, with the version found and how to upgrade. A server that does not report its version (`MODULE LIST` refused by an ACL, or disabled) is let through with a warning; an error reply that passes, such as `TRYAGAIN`, is retried like a query; one that cannot be asked, after the usual retries, fails that query with `DatabaseUnavailableError` — no query runs unchecked — and is asked again by the next.

```python
from graphrag_sdk import FalkorDBVersionError

try:
    await rag.ingest("report.pdf")
except FalkorDBVersionError as e:
    print(e)  # names the version found and the minimum, 4.20
```

**Supported engines.** FalkorDB ships two engines: 4.x is the C engine and 6.x the Rust engine. They differ in index DDL, procedures, error text and the order of unordered rows, and the SDK runs on both. CI runs the integration suite against a pinned release of each, `v4.22.2` and `6.0.2`; `docker-compose.yml`, the examples and the `docker run` lines in these docs use `falkordb/falkordb:v4.22.2`.

**Upgrade order.** Upgrade the FalkorDB server to 4.20 or later *first*, then the SDK: the SDK refuses an older server rather than running on it. A graph built on an older server needs no migration. Entities it already holds vectors for count as checked, and new ones are checked by the next `finalize()`; to check every entity once, run `finalize(dedup_all=True)`.

### Deterministic Results

FalkorDB 4.x and 6.0.x list unordered rows differently, so any result cut by a `LIMIT` or a cap would change after a server upgrade. The SDK orders before it cuts:

- `search_chunks()` and `search_entities()` break ties by id (see [Search Methods](#search-methods)); fulltext search orders by score, then id.
- `get_connected_entities()` keeps the 50 entities with the lowest ids at `max_hops=1`. Beyond one hop the engine's order is kept, because ordering would need every path before the `LIMIT`.
- The relation-pattern backfill orders the chunk pairs its cap shows the LLM; `GraphVisualizer.sample_nodes()` and a new relation pattern's copied properties are ordered too.
- A dedup merge's survivor is ranked down to the id, so a tie settles the same way on every run.

### Vector Storage

FalkorDB stores vectors as `vecf32` — a native 32-bit float vector type. All vectors in the SDK are stored via:
```cypher
SET n.embedding = vecf32($vector)
```

### Vector Search API

Node vector search uses 4 arguments:
```
db.idx.vector.queryNodes('Label', 'property', $top_k, vecf32($vector))
```

Relationship vector search:
```
db.idx.vector.queryRelationships('RELATES', 'embedding', $top_k, vecf32($vector))
```

### Graph Deletion

`rag.delete_all()` deletes the graph with `GRAPH.DELETE` (the Redis-level command), and drops its paired ontology graph too:
```python
await rag.delete_all()  # Uses GRAPH.DELETE internally
```
This is much faster than `MATCH (n) DETACH DELETE n` on large graphs. The indexes go with the graph, and the SDK forgets which ones it created, so the next ingest creates them again before it writes.

### Retry Behavior

The connection layer makes up to `retry_count` attempts per query (default 3: the first try and two retries), with exponential backoff and jitter between them (`retry_delay * 2^attempt * random(0.5, 1.5)`), and employs a circuit breaker to short-circuit repeated failures. Everything that is not a server reply is retried (a lost connection or socket timeout, `LOADING`), and of the server's replies only the temporary ones (a full query queue, `BUSY`, `NOREPLICAS`, `MISCONF`, a cluster redirect or failover, a read-only replica, out of memory); one that outlasts every attempt raises `DatabaseUnavailableError`. A query the server rejects, or one it stops with "Query timed out", raises `DatabaseError` at once, without retrying; a rejection counts as a healthy answer for the circuit breaker. If you catch `DatabaseUnavailableError` to detect an outage, catch `DatabaseError` for these.

**Timeouts.** The server stops a read at `query_timeout_ms` (default 10,000 ms). The client waits `query_timeout_ms` + 5 s for each reply (with no limit when `query_timeout_ms` is `None`), so a query that takes 5–10 s gets its answer instead of failing on the client. Opening a connection and `ping()` still give up after 5 s, and the driver's first probe of the server waits 5 s for each reply, though redis-py retries that probe on its own (measured with redis-py 8.1: about 60 s against a server that accepts connections and never answers, before `DatabaseUnavailableError`). On a server that stops answering queries once the connection is open, a query raises `DatabaseUnavailableError` after about 48 s at the defaults (46–50 s, with the jitter): each of the `retry_count` attempts waits `query_timeout_ms` + 5 s, plus the backoff between them. Lower `query_timeout_ms` or `retry_count` to fail sooner. See [Configuration](/configuration#retry-behavior).
