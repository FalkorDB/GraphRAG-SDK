title: "Incremental Updates"
description: "Update, delete, and re-index documents and tables in an existing graph without a full re-ingest, then run finalize() once."
---

Once a graph has been ingested, real corpora keep changing: documents get edited, replaced, or removed, and tables get new exports. Re-running a full ingest on every change is expensive and discards the existing graph. The incremental update primitives let you mutate an already-built graph in place, with crash-safe semantics and scoped orphan cleanup.

This page is the API reference and usage guide for those primitives:

- [`update()`](#update) — re-sync a single document or table
- [`delete_document()`](#delete_document) — remove a single document and its orphans
- [`apply_changes()`](#apply_changes) — heterogeneous batch (added / modified / deleted)
- [`finalize()`](#finalize) — run once at the end of a batch

The canonical use case is **CI-driven graph updates on PR merge**: a typical diff has all three change types in one go, and `apply_changes()` routes each list to the right primitive.

---

## Mental Model — What Lives in the Graph

To understand the effect of each primitive, it helps to know the node shapes the lexical graph keeps:

| Label              | Purpose                                                                 |
| ------------------ | ----------------------------------------------------------------------- |
| `Document`         | One per ingested source. Carries `content_hash`, `path`, how it was written (prose or records), and metadata. |
| `Chunk`            | Linked to its `Document` via `PART_OF`. Holds embeddings. A table row is a chunk too (`kind: "record"`). |
| `__Entity__`       | Extracted entities and table rows. Linked to chunks via `MENTIONED_IN`. Carries `source_chunk_ids`, the union of every chunk that mentioned it. |
| `RELATES` (edge)   | Fact between two entities, keyed on its `rel_type`. Carries `source_chunk_ids` for provenance. |

Incremental updates are scoped via these relationships — orphan cleanup never goes global, it only inspects entities the touched document actually referenced.

---

## Document Ids and the Content Hash

Every primitive addresses a `Document` by its id:

| How it was ingested | Default id |
| --- | --- |
| A file path | The normalised path (`./docs/a.md` and `docs/a.md` are one document). A URI source (`https://...`, `s3://...`) is used verbatim |
| A table (`.csv`, `.tsv`, `.psv`, `.tab`) | The table's name: the basename of its mapping's `source`, so a new export under another directory re-syncs the same table |
| `text=` without `document_id` | `text-<16 hex>`, derived from a hash of the text, so the same text twice is one document |

Pass `document_id=` to choose your own. An id may not contain the reserved marker `__pending__` (`ValueError`), which the update cutover uses for its transient documents.

The pipeline stores a SHA-256 `content_hash` on the Document. Re-ingesting or updating byte-identical content is a no-op: `ingest()` of prose returns before chunking with `metadata["skipped_unchanged"] = True` and `chunks_indexed = 0`, `ingest()` of a table returns a `StructuredIngestionResult` with `no_op=True`, and `update()` returns `no_op=True`. No chunker, extractor, LLM or graph write runs. For a table the hash covers the mapping as well as the rows, so re-declaring a column's type is never mistaken for unchanged data.

The hash is written last, and only when every write was reported in full. A failed extraction, an edge the graph store dropped after a transient error, or a chunk left without an embedding withholds it, and `metadata["incomplete_writes"]` lists the shortfalls. The next `ingest()` or `update()` of that content then runs again and repairs the document instead of skipping it.

Chunk ids are derived from the document id, the chunk's position and its text, so re-ingesting the same file writes onto the same chunk nodes. Inserting a paragraph re-ids every later chunk; only byte-identical files are a no-op.

## `update()`

Re-sync a previously-ingested document. The new content replaces the old chunks, entities are re-extracted, and entities that become orphaned (no remaining `MENTIONED_IN` edges) are cleaned up along with their incident `RELATES` edges.

```python
result = await rag.update(
    source=None,                    # OR text=...
    text=None,
    document_id=None,
    loader=None,
    chunker=None,
    extractor=None,
    resolver=None,
    cache_unchanged_chunks=False,
    if_missing="error",             # "error" | "ingest"
    force=False,
    record_loader=None,             # tables only
    strict_mapping=False,           # tables only
    ctx=None,
)
```

`update_sync()` takes the same arguments.

### Parameters

| Argument                                | Meaning                                                                                                                                                           |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `source`                                | File path. Mutually exclusive with `text`. In file mode, `document_id` defaults to the same id `ingest(source)` derives (see [Document Ids](#document-ids-and-the-content-hash)). |
| `text`                                  | Raw text. Skips the loader. Requires an explicit `document_id`.                                                                                                   |
| `document_id`                           | Stable id of the `Document` node to update. Required for text mode.                                                                                               |
| `loader` / `chunker` / `extractor` / `resolver` | Per-call strategy overrides, identical to `ingest()`. `chunker` and `extractor` are refused (`ValueError`) for a table.                                   |
| `cache_unchanged_chunks`                | `False` (default) re-extracts every chunk. `True` reuses the graph's existing extraction for new chunks whose text is byte-identical to a chunk of this document. See [Chunk-level extraction cache](#chunk-level-extraction-cache). Refused for a table. |
| `if_missing`                            | `"error"` (default) raises `DocumentNotFoundError` if the id is unknown. `"ingest"` falls through to a fresh `ingest()` — upsert semantics.                       |
| `force`                                 | `False` (default) returns `no_op=True` when the content hash is unchanged. `True` re-extracts anyway — the way to apply a new ontology, chunker, extractor or model to existing text, since `ingest()` also skips unchanged documents. Keep `cache_unchanged_chunks=False` with it, or the cache hands back the previous extraction. |
| `record_loader` / `strict_mapping`      | For a table only, identical to `ingest()`: how to read the source, and whether a column the mapping never reads is an error. Refused (`ValueError`) for prose.     |

### Returns — `UpdateResult`

```python
UpdateResult(
    document_info: DocumentInfo,
    nodes_created: int,
    relationships_created: int,
    chunks_indexed: int,            # new chunks written
    chunks_deleted: int,            # old chunks removed
    entities_deleted: int,          # orphan entities pruned
    no_op: bool,                    # True if content_hash matched
    replaced_existing: bool,        # False if if_missing="ingest" upserted
    metadata: dict[str, Any],       # e.g. "cache_stats", "incomplete_writes"
)
```

For a table, `metadata` carries the structured counts (`records`, `entities`, `references`, `edges`, ...) of the [`StructuredIngestionResult`](/structured-ingestion).

### Effect on the graph

| Scenario                                  | What changes                                                                                                                                                                                 |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Content hash matches (touch-only edit)    | **Nothing.** SHA-256 short-circuits the call to a single Cypher lookup. `no_op=True`. Use this for CRLF/formatter-only PRs. Pass `force=True` to re-extract regardless.                     |
| Real content change                       | New chunks written under a pending Document, then atomically cut over to the canonical id. Old chunks are deleted. Entities previously mentioned only by this document are removed.          |
| Entity still referenced by another doc    | **Preserved.** Orphan cleanup is scoped to candidates from this document — never global. The deleted chunks are removed from its `source_chunk_ids`.                                       |
| `RELATES` edge sourced only from old chunks | **Removed** as a stale fact (cleanup keyed on `source_chunk_ids`).                                                                                                                          |
| `if_missing="ingest"` and id unknown      | Behaves like a fresh `ingest()`. `replaced_existing=False`.                                                                                                                                  |
| A table's new export                      | A **re-sync**: a row deleted from the export is removed, a blanked cell loses its column, a moved foreign key leaves its old target, and a node another source still mentions survives with the table's signed columns and identity taken back. See [Structured Ingestion](/structured-ingestion). |

A Document records how it was written. Updating a table's Document from a prose file, or a prose Document from a table, raises `ValueError` rather than re-reading one as the other; `delete_document()` it first if the source really changed kind.

### Crash safety — the pending-document cutover

The new content is written under a transient pending Document (`<id>__pending__<8 hex>`) beside the live one, so the live document stays readable while the update runs. The cutover is a state machine with one load-bearing commit point (`mark_pending_committed`, which sets `ready_to_commit` on the pending Document):

- Before the commit, a crash rolls back: the pending data is discarded and the live document is untouched.
- After the commit, a crash rolls forward: the old chunks are deleted, the pending Document is renamed to the canonical id, and orphan cleanup runs. The cleanup state is written onto the pending Document before the commit, so it survives the crash.

Every `update()` and `delete_document()` against an id first finishes or rolls back whatever a crashed call left on it. Chunks written by `update()` are keyed on the transient pending id, so the pending and live documents never share chunk nodes during the cutover.

### Chunk-level extraction cache

`update(..., cache_unchanged_chunks=True)` makes editing one paragraph of a 50-chunk document cost about one LLM extraction instead of fifty. New chunks whose text is byte-identical to an existing chunk of the same document skip extraction: their entities, relationships and mentions are rebuilt from the live graph and remapped onto the new chunk ids. Only new or changed chunks go to the extractor. `UpdateResult.metadata["cache_stats"]` reports `cached_chunks` and `extracted_chunks`.

The cache fails open per chunk: a chunk it cannot rebuild is re-extracted, along with any chunk that depends on it. An unreachable graph (`DatabaseUnavailableError`) and an exhausted latency budget propagate instead, since extraction would bill in full and then fail at the write. A query the server rejects (`DatabaseError`) falls back to extraction.

<Warning>
The graph is the cache. Entities you deleted by hand are not brought back from unchanged chunks, and a change of ontology, prompt or model does not re-extract unchanged chunks. Leave `cache_unchanged_chunks=False` (the default) to force a full rebuild in those cases.
</Warning>

The underlying decorator, `CachedChunkExtraction(inner, graph_store, document_id)`, is exported for custom pipelines.

### Example

```python
# Initial ingest with a stable id
await rag.ingest(text=V1_TEXT, document_id="alice_bio")

# Touch-only — short-circuits via content hash
result = await rag.update(text=V1_TEXT, document_id="alice_bio")
assert result.no_op is True

# Real edit — replaces chunks, prunes orphans
result = await rag.update(text=V2_TEXT, document_id="alice_bio")
print(f"replaced {result.chunks_deleted} chunks, "
      f"removed {result.entities_deleted} orphan entities, "
      f"wrote {result.chunks_indexed} new chunks")

# Small edit to a long document — reuse the unchanged chunks' extraction
result = await rag.update(text=V3_TEXT, document_id="alice_bio", cache_unchanged_chunks=True)
print(result.metadata.get("cache_stats"))
```

## `delete_document()`

Remove a single document and everything it uniquely owns.

```python
result = await rag.delete_document(
    document_id: str,
    *,
    if_missing="error",             # "error" | "ignore"
)
```

`delete_document_sync()` takes the same arguments.

### Parameters

| Argument      | Meaning                                                                                                                                                                                |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `document_id` | The Document node id (see [Document Ids](#document-ids-and-the-content-hash)). Empty raises `ValueError`.                                                                               |
| `if_missing`  | `"error"` (default) raises `DocumentNotFoundError`. `"ignore"` returns an empty result with zero counts — useful for CI deletes when the caller doesn't track which files were ever ingested. |

### Returns — `DeleteDocumentResult`

```python
DeleteDocumentResult(
    document_uid: str,
    chunks_deleted: int,
    entities_deleted: int,
)
```

### Effect on the graph

| What is removed                                                                  | Notes                                                                |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| All `Chunk` nodes linked to the Document via `PART_OF`                           | Unconditional — the chunks belong only to this Document.             |
| The `Document` node itself                                                       | Removed last, after cleanup completes.                               |
| `__Entity__` nodes that the doc referenced and have **no** remaining `MENTIONED_IN` | Scoped to candidates from this document; entities still cited elsewhere are kept, minus the deleted chunks in their `source_chunk_ids`. |
| `RELATES` edges whose `source_chunk_ids` are entirely from this Document's chunks | Stale-fact cleanup. Edges with multi-document provenance survive.    |
| For a table: the columns it signed on entities that survive                      | A node another source still mentions keeps its name and prose facts and loses the table's columns and identity. |

To take a table out entirely, including its stored mapping, use [`drop_table()`](/structured-ingestion), which calls `delete_document()` for the table's rows and then removes what it signed.

### Crash safety

A single atomic write (`pending_delete=true` + cleanup-state arrays on the doc) is the commit marker. Before that write the live document is untouched. After it, every remaining step is idempotent and resumes on the next call against this id.

### Example

```python
await rag.delete_document("alice_bio")

# Idempotent cleanup of files removed in a PR — never errors if unknown
await rag.delete_document("some/path.md", if_missing="ignore")
```

## `apply_changes()`

Heterogeneous batch — the convenience wrapper for CI-driven incremental ingestion. Dispatches each list to the right primitive in a fixed order:

1. `deleted` → `delete_document()`
2. `modified` → `update(if_missing="ingest")` (so a "modified" file the graph has never seen is upserted, not errored)
3. `added` → `ingest()`

```python
result = await rag.apply_changes(
    *,
    added=None,
    modified=None,
    deleted=None,
    loader=None,
    chunker=None,
    extractor=None,
    resolver=None,
    cache_unchanged_chunks=False,   # for `modified`
    max_concurrency=3,              # for `added`
    update_concurrency=1,           # for `modified` — see warning below
    ctx=None,
)
```

`apply_changes_sync()` takes the same arguments.

### Parameters

| Argument             | Meaning                                                                                                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `added`              | New file paths to ingest.                                                                                                                                                                              |
| `modified`           | File paths whose content changed.                                                                                                                                                                      |
| `deleted`            | Document ids (typically file paths) to remove.                                                                                                                                                         |
| `loader` / `chunker` / `extractor` / `resolver` | Strategy overrides forwarded to the add/update path. Ignored for deletes.                                                                                                                  |
| `cache_unchanged_chunks` | Forwarded to `update()` for the `modified` list. See [Chunk-level extraction cache](#chunk-level-extraction-cache).                                                                                |
| `max_concurrency`    | Parallelism cap for `ingest()` of the `added` list. Safe to raise — adds have no orphan-cleanup race surface.                                                                                          |
| `update_concurrency` | **Default 1, and you almost certainly should not raise it.** The orphan-cleanup invariant only holds while updates serialize. See [Concurrency](#concurrency-and-the-update_concurrency-trap) below.   |

The order `deletes → updates → adds` is part of the public contract; do not assume reordering is safe.

Overlapping ids across input lists raise `ValueError` at the input boundary — this is almost always a broken git-diff parser.

**Tables in a batch.** A table (`.csv`, `.tsv`, `.psv`, `.tab`) in `added` or `modified` is written on its own through the structured path its mapping describes, one source at a time, so one bad row cannot fail the rest of the batch. The `chunker`, `extractor`, `resolver` and `cache_unchanged_chunks` overrides apply to the prose in the batch, not to tables. A table's entry carries the structured counts (`records`, `entities`, `references`, `edges`) in its result's `metadata`.

### Returns — `ApplyChangesResult`

```python
ApplyChangesResult(
    added:    list[BatchEntry[IngestionResult]],
    modified: list[BatchEntry[UpdateResult]],
    deleted:  list[BatchEntry[DeleteDocumentResult]],
)
```

Each entry aligns by index with the corresponding input list. Per-file errors are wrapped as `BatchEntry` with `error` (string) and `error_type` (exception class name) set; the batch never raises. Branch on `entry.is_success`:

```python
for entry in result.modified:
    if entry.is_success:
        ...   # entry.result is an UpdateResult
    elif entry.error_type == "DocumentNotFoundError":
        ...
```

### Effect on the graph

`apply_changes()` does not itself touch the graph — it dispatches to the primitives documented above and aggregates their results. Two whole-batch consequences worth knowing:

- **No automatic `finalize()`.** Call `finalize()` once after the batch, not once per file. Its dedup checks only the entities whose check is pending — the ones the batch added, which have no name vector yet, and any an earlier run left pending — so one call judges the whole batch's new entities together, in fewer LLM calls than one per file, and a second call with nothing pending does no dedup work.
- **Peak entity cardinality is minimised** because deletes run first — orphan candidates are gone before adds can re-introduce overlapping ids.

### Canonical CI usage

```python
async with GraphRAG(connection=..., llm=..., embedder=...) as rag:
    await rag.apply_changes(**parse_git_diff(pr_sha, base_sha))
    await rag.finalize()
```

### Concurrency and the `update_concurrency` trap

Raising `update_concurrency` above 1 is unsafe in general because the orphan-cleanup correctness proof relies on `MENTIONED_IN` edges being persisted before any cutover begins. Two concurrent updates sharing an entity `e1` are only guaranteed to preserve it because:

- Pre-cutover, `e1` still has its old `MENTIONED_IN` edges.
- Post-`pipeline.run()` (but pre-cutover), the new `MENTIONED_IN` edges are already written.

So an update doing orphan cleanup will always see at least one incident edge. Raising the default to ≥2 is **only safe** if you can independently guarantee that no two parallel updates can share an entity in their candidate snapshots. The integration test `test_concurrent_updates_preserve_shared_entity` is the tripwire for this invariant — break it before bumping the value.

Concurrent updates to the **same** `document_id` are not supported: serialize them yourself.

## Updates While `finalize()` Runs

`update()`, `delete_document()`, `drop_table()` and a table re-sync never wait for a running `finalize()`. Every SDK query that deletes or re-keys an entity also leaves a `deleted` record, in the same query, while a dedup run is in progress. A merge the run planned that would touch such an entity is skipped, nothing is written for it, and its group is decided again on the next `finalize()`; `FinalizeResult.dedup_merges_changed` counts these. Deletes you issue with your own Cypher are not covered. See [Storage](/storage#running-alongside-update-and-deletes) for how this stays consistent.

## `finalize()`

Run **once** after a batch of ingests/updates/deletes. Skipping it leaves cross-document duplicates in place and disables entity-/edge-level vector search. A read on a graph with documents ingested since the last dedup logs a warning that names the missing step.

```python
result = await rag.finalize(
    *,
    judge=None,          # a DedupJudge; None = LLMJudge(rag.llm)
    dedup_all=False,     # check every entity, and retry the unresolved ones
)
```

`finalize_sync()` takes the same arguments.

| Argument | Meaning |
| --- | --- |
| `judge` | Who decides which candidates are one entity: any `DedupJudge`. Defaults to `LLMJudge` with the instance's `llm`. A gpt-4.1-class model is strongly recommended for the judge: on the benchmark corpus it made 9 wrong merges where gpt-4o-mini made 51, so pass `judge=LLMJudge(stronger_llm)` if your `llm` is small. `judge=False` raises `TypeError`: every run has a judge. |
| `dedup_all` | `False` checks only the pending entities. `True` checks every entity once and retries the unresolved ones — for a graph whose entity vectors were written outside `finalize()`, such as one whose entities were embedded before you upgraded the SDK. |

`finalize()` raises `DedupRunActiveError` when another `finalize()` is already deduplicating the same graph, from any process or from the same `GraphRAG`; the running one is left untouched. It raises `FalkorDBVersionError` before anything is written when the server is older than FalkorDB 4.20.

### What it does (in order)

1. Removes NULL-name stub entities (legacy cleanup). Entities a table wrote are never removed here, since a table may have no name column.
2. `deduplicate_entities()` — incremental: the pending entities (added since the last `finalize()`, or left pending by it) are checked against the whole graph through the `__Entity__` vector index — the exact phase by canonical name, then one judge pass over each pending entity and its nearest names. Every merge is written as a sealed plan and applied one atomic query at a time, so an interrupted `finalize()` is finished by the next one. Dedup also writes every new entity's name embedding (there is no separate entity backfill step). See [Storage](/storage) for the full algorithm.
3. `embed_relationships()` — embeds fact text on `RELATES` edges.
4. `ensure_indices()` — rebuilds/verifies all indexes and waits for any build in progress.
5. Checks the graph for what it should report — signed properties left behind, properties more than one table supplies, mappings nobody declared, placeholders nothing filled, entities without a name, near-duplicates that did not merge — and logs each finding at WARNING. Nothing in this step changes the graph.

`finalize()` calls the LLM through the default judge. To keep it LLM-free, pass a `DedupJudge` of your own (see [Storage](/storage#the-judge-component)).

### FinalizeResult

`finalize()` returns a typed `FinalizeResult`. Nothing it reports is resolved for you; every non-empty list or dict of findings is also logged at WARNING (`judge_stats` and `indexes` are logged at INFO).

**Counts from the steps**

| Field | Type | Meaning |
| --- | --- | --- |
| `null_stubs_removed` | `int` | NULL-name stub entities removed in step 1 |
| `entities_deduplicated` | `int` | Duplicates merged, both phases, including merges finished from an interrupted run's plan |
| `entities_embedded` | `int` | Entity name vectors dedup wrote this run |
| `relationships_embedded` | `int` | `RELATES` facts embedded |
| `indexes` | `dict[str, bool]` | Each index `ensure_indices()` checks (`range_ids`, `vector_Chunk`, `vector_Entity`, `vector_RELATES`, `fulltext_Chunk`, `fulltext_Entity`), and whether it is in place: `True` when created now or already there, `False` when creation failed. `finalize()` forces the check, so every key is always present |

**Dedup**

| Field | Type | Meaning |
| --- | --- | --- |
| `judge_calls` | `int` | Calls to the judge: one per round, the first ask and each re-ask of sets without a usable answer. The number of LLM prompts is `judge_stats["llm_calls"]` |
| `judge_stats` | `dict[str, int \| str]` | The judged phase's counts: `entities`, `neighbours`, `candidates`, `sets`, `judge_calls`, `judge_failed`, `unanswered_sets`, `agreed_pairs`, `merged`, plus what the judge reports through `usage()` (`llm_calls`, `llm_failed` for `LLMJudge`) |
| `dedup_pending` | `int` | Entities still pending after this run: a failed lookup or judge call, an answer that was not a clean partition, a group held because one of its sets got no verdict, or a merge an `update()` changed. The next `finalize()` checks them again |
| `dedup_unresolved` | `list[str]` | Entities no longer retried: 3 judged runs left their check incomplete (no usable verdict, an interrupted run, or a merge an `update()` changed). Each entry names the entity, the last reason, the number of judged runs and the entities it was kept from being judged with. Never merged automatically; `finalize(dedup_all=True)` retries them |
| `dedup_merges_changed` | `int` | Planned merges skipped because an entity changed while the run applied them — deleted or re-keyed by `update()`, renamed, or rewritten too often to read. Nothing was written for them; their groups are decided again next run |
| `dedup_collisions` | `list[str]` | Merges whose two entities held different values for one property, e.g. `"Tim Cook: born kept 1960 (judge), dropped 1961 from Timothy Cook"`. The other value is kept on the merged entity in `<property>__dropped` |
| `probable_duplicates` | `list[str]` | Same-label entities that probably denote one thing and did not merge, with the reason — spellings the canonical form does not join (`M. Ellison` / `Maya Ellison`) that the judge left apart, and mentions of a name two keyed rows share |
| `unmerged_name_collisions` | `dict[str, list[str]]` | Names that exist under more than one label, mapped to those labels. Never merged (Apple the company and Apple the fruit); also the sign of documents ingested before a table mapping declared their label |

**Structured sources** (see [Structured Ingestion](/structured-ingestion))

| Field | Type | Meaning |
| --- | --- | --- |
| `property_conflicts` | `list[str]` | One property supplied by more than one table, with how many entities hold a value from more than one table and on how many they differ, e.g. `"Person.grade — supplied by finance.csv, hr.csv; 1 of 2 entities hold different values"`. Every value is kept, signed by its table |
| `unresolved_references` | `dict[str, int]` | Per label, placeholders a foreign key created that no source ever filled in |
| `entities_without_a_name` | `dict[str, int]` | Per label, mapped entities with no display name; they can never join a document mention |
| `proposed_mappings` | `list[str]` | Tables running on a mapping the SDK proposed because none was declared |
| `mapping_changed` | `list[str]` | Tables whose declared mapping differs from the stored one; properties it no longer declares were removed from the nodes |
| `stale_signed_properties` | `list[str]` | Signed properties left on an entity by a table that no longer mentions it — from a graph written before the retraction existed, or an interrupted cleanup |

```python
result = await rag.finalize()
print(f"merged {result.entities_deduplicated}, "
      f"{result.judge_stats.get('llm_calls', 0)} judge prompts, "
      f"{result.dedup_pending} still pending")
for line in result.dedup_unresolved + result.probable_duplicates:
    print("check:", line)
```

<Note>
**An existing graph.** On a graph whose entities already have name vectors, those entities count as checked; the next `finalize()` checks only the new ones. To check every entity once, run `finalize(dedup_all=True)`. Upgrade the FalkorDB server to 4.20 or later before the SDK: see [Storage](/storage#version).
</Note>

## Choosing the Right Primitive

| Situation                                                                | Use                                       |
| ------------------------------------------------------------------------ | ----------------------------------------- |
| Single doc, you know it exists and the text changed                      | `update(...)`                             |
| Single doc, small edit to a long document                                | `update(..., cache_unchanged_chunks=True)` |
| Single doc, unchanged text but a new ontology, chunker or model          | `update(..., force=True)`                 |
| Single doc, may or may not exist (upsert)                                | `update(..., if_missing="ingest")`        |
| Single doc, remove it                                                    | `delete_document(...)`                    |
| Single doc, remove it but the caller is not sure it was ever ingested    | `delete_document(..., if_missing="ignore")` |
| A table's new export                                                     | `update("employees.csv")` or `ingest("employees.csv")` — both re-sync |
| A table and its mapping, gone for good                                   | `drop_table("employees.csv")`             |
| PR diff or any heterogeneous batch                                       | `apply_changes(added=..., modified=..., deleted=...)` then `finalize()` |
| Just added/changed one doc and you're about to query                     | `ingest()` or `update()` then `finalize()` |
